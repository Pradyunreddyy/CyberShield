# Security Considerations & Testing

This document lists the security risks considered for this project, what was implemented to mitigate them, and how each was tested. No vulnerabilities were intentionally left in the code for demonstration purposes.

| Risk | Mitigation | How it was tested |
|---|---|---|
| **Plaintext passwords** | Passwords are hashed with bcrypt (`passlib`) before storage; the hash is never returned by any API response (`UserOut` schema excludes it). | Verified `hashed_password` is never present in `/api/auth/me` or `/api/admin/users` responses; login fails for wrong passwords (`test_login_invalid_credentials`). |
| **Broken authentication** | JWT bearer tokens signed with `JWT_SECRET_KEY`, expiring after `ACCESS_TOKEN_EXPIRE_MINUTES`. Disabled accounts are rejected at login and via `get_current_user`. | `test_protected_route_requires_token`, `test_protected_route_rejects_invalid_token`, `test_disabled_user_cannot_login`. |
| **Broken authorization / missing access control** | Every state-changing and role-sensitive route depends on `require_roles(...)`, enforced **server-side** regardless of what the frontend shows. Developers are further restricted to their own reported incidents/scans at the repository-query level, not just via a response filter. | `test_developer_cannot_create_incident`, `test_unauthorized_role_cannot_delete_incident`, `test_non_admin_cannot_list_users`, `test_developer_cannot_view_others_scan`, `test_developer_cannot_use_ai_analyzer`. |
| **SQL injection** | All queries go through SQLAlchemy's ORM/Core query builder with bound parameters — no raw string-interpolated SQL exists anywhere in the codebase. | Manual code review of every `repositories/*.py` file; search-by-title uses `ilike()` with a bound parameter, not string formatting. |
| **Invalid/forged JWTs** | `python-jose` verifies signature and expiry; any decode failure raises `InvalidTokenError`, mapped to `401`. | `test_protected_route_rejects_invalid_token`. |
| **Unsafe file uploads** | Extension allow-list **and** magic-byte verification (not just trusting the client's filename/extension); enforced max size; server-generated random filename; upload is never written to a web-servable path. | `test_reject_non_zip_extension`, `test_reject_file_too_large`. |
| **Path traversal in archive extraction ("zip slip")** | Every archive member's resolved path is checked with `os.path.commonpath` to guarantee it stays inside the extraction sandbox; absolute paths, drive letters, and symlink entries are rejected outright. | Implemented in `scanners/archive_handler.safe_extract`; covered indirectly by `test_upload_and_scan_detects_suspicious_pattern` (extraction must succeed safely for analysis to run at all). |
| **Archive/zip bombs** | Hard caps on entry count (`MAX_FILES_PER_ARCHIVE`) and total uncompressed size (`MAX_UNCOMPRESSED_ARCHIVE_BYTES`), checked *before* any bytes are written to disk. | Code review of `safe_extract`; limits are configurable via environment variables. |
| **Arbitrary code execution from uploads** | Uploaded projects are **never executed, imported, or `eval`'d** at any point. Static analysis only opens files as text with a byte-size cap per file. | Code review — no `subprocess`, `exec`, `eval`, or dynamic import touches uploaded content anywhere in `scanners/`. |
| **XSS via user-provided content** | React escapes all interpolated text by default (no `dangerouslySetInnerHTML` is used anywhere in the frontend); incident titles/descriptions/notes are rendered as plain text. | Code review of `frontend/src` — zero occurrences of `dangerouslySetInnerHTML`. |
| **CORS misconfiguration** | `CORS_ORIGINS` is an explicit, comma-separated allow-list read from the environment; the code never falls back to `"*"`. | Code review of `main.py`; `.env.example` documents this explicitly. |
| **Unsafe error messages / stack trace leakage** | A global exception handler catches unhandled exceptions, logs the full traceback server-side, and returns a generic `500` message to the client. Validation errors return structured (but non-sensitive) field errors. | Code review of `main.py`'s exception handlers. |
| **Secrets in source control / logs** | All secrets (DB URL, JWT secret, AI API key) are read from environment variables via `pydantic-settings`; `.env` is gitignored; the audit log service explicitly strips any key matching `password`, `token`, `secret`, or `api_key` before writing. | Code review of `core/config.py` and `services/audit_service._sanitize`. |
| **Hardcoded credentials shipped in the repo** | None exist. Demo account passwords are seeded only when the `users` table is empty and are clearly documented as demo-only in the README. | Code review of `app/seed.py`. |

## What was intentionally out of scope

- **Live vulnerability/CVE lookups** for dependencies — the dependency analyzer is heuristic only (unpinned versions, install scripts, raw URL sources) and does not call any external vulnerability database, since scanning untrusted uploads should not trigger outbound network calls.
- **Real malware detection** — the platform is explicit (in the UI and in prompts sent to the AI) that findings are "potentially suspicious," never a definitive malware verdict. The architecture (`ai/providers.py`'s pluggable provider pattern) is designed so a real antivirus/malware-scanning API could be added later without changing calling code.
- **Rate limiting / brute-force lockout** — reasonable for a semester project to note as a "next step" rather than implement, given the scope constraints in this brief.
